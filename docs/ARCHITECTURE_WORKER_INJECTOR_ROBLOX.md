# Схема: воркер + инжектор + изолированные сессии Roblox

Целевая архитектура для одного Windows-сервера с десятками ботов в Creatures of Sonaria: воркер управляет изолированными процессами Roblox (по сути — по одному на аккаунт в отдельной сессии Windows), внешний инжектор подгружает Lua, статус возвращается через IPC (в т.ч. уже существующий файловый мост).

> **Важно:** инжекция и обход античита нарушают правила Roblox и могут повлечь блокировки. Этот документ описывает **техническую** схему; ответственность за соответствие ToS и законам — на стороне развёртывания. Инжектор и Lua не входят в репозиторий `sonaria_farm`.

Текущий код в репозитории закрывает: **БД, бот, очередь, воркер, `WindowsGameAdapter` с файловым мостом** (`farm_tick`, `transfer`, `sell`, `login_and_check` через каталоги — см. `farm/game/file_bridge.py`). Запуск Roblox под другим пользователем, `CreateProcessAsUser` / `runas` и вызов инжектора — **предстоит доработать** в адаптере или в отдельном sidecar.

## 2. Изоляция сессий Roblox

Roblox обычно не даёт несколько клиентов в одной пользовательской сессии Windows так, как нужно ферме. Рабочая идея:

- На каждый игровой аккаунт (или группу) — **отдельный пользователь Windows**.
- Соответствие вроде: `account.id` → имя пользователя `rbx_<short_hash>` (политика имён — на стороне деплоя).
- Пароль пользователя Windows хранится **вне git** (секреты, DPAPI, менеджер секретов).

Воркер для `WORKER_ACCOUNT_ID`:

1. Проверяет, запущен ли уже Roblox для этого аккаунта (PID в памяти воркера и/или запись в БД/`instances`).
2. Если нет — стартует процесс от нужного пользователя (`runas`, `CreateProcessAsUser`, планировщик и т.д. — выбор зависит от инфраструктуры).
3. Сохраняет PID и связь `account_id` ↔ процесс.

## 3. Инжектор

Отдельная программа (C++/C# и т.д.):

- Аргументы: `<PID> <script.lua> [json_args]`.
- Поиск процесса, загрузка/исполнение Lua в контексте клиента (механизм — за пределами этого репо).

Путь к exe задаётся окружением, например **`INJECTOR_PATH`**. Если путь содержит пробелы (`Program Files`), в `.env` используй кавычки:  
`INJECTOR_PATH="C:\Program Files\jjsploit\jjsploit.exe"` (пример из `env.template`).

В репозитории реализован **опциональный** запуск через `subprocess` в **`farm/game/injector_launcher.py`**:  
`INJECTOR_ENABLED=1`, `INJECTOR_LAUNCH_WHEN=windows_adapter_init` (один раз при первой операции моста в процессе воркера) или `every_farm_tick` (на каждый `farm_tick`). Аргументы CLI — `INJECTOR_ARGS_JSON` (массив строк), если твой exe их поддерживает.

Параметры для Lua в JSON моста — объект **`script_params`**, см. **[SCRIPT_PARAMS_AND_LUA.md](SCRIPT_PARAMS_AND_LUA.md)**.

## 4. Взаимодействие воркера с Lua

**Файловый IPC** уже используется: воркер пишет `request`, внешний процесс (инжектор + игра) отвечает `response`. См. [EXTERNAL_BRIDGE_CLIENT.md](EXTERNAL_BRIDGE_CLIENT.md) и [README.md](../README.md) (форматы JSON, опционально `inventory`).

Для **долгого фарма** (`start_farm`):

- Сейчас модель: **каждый тик** — один обмен `farm_tick` (request/response). Это совместимо с «скрипт делает один шаг и выходит».
- Альтернатива из твоей схемы: один долгий Lua-цикл + сигнал остановки (`stop_<account_id>.flag` или повторная инжекция `stop_farm.lua`). Тогда нужно менять семантику задачи в воркере (одна RUNNING-задача, lease, отмена через флаг) — это **расширение** относительно текущего пошагового `farm_tick`.

Имеет смысл фиксировать выбранную модель в коде/доке при реализации.

## 5. Последовательность по типам задач (целевое поведение)

| Задача | Идея |
|--------|------|
| `login_and_check` | Старт Roblox при необходимости → инжекция `check_login.lua` → файл статуса → обновление `accounts.status` (сейчас частично через `LOGIN_CHECK_RESULTS_DIR`). |
| `start_farm` | Roblox уже есть → параметры `targetDP` → фарм-логика; остановка по cancel / `stop_farm` + флаг или пошаговый `farm_tick` как сейчас. |
| `transfer_to_storage` | `transfer.lua` + payload из бота; ответ с `ok` / `inventory` и т.д. |
| `set_sell_price` | `sell.lua` + ranges / приоритеты. |

## 6. Несколько воркеров на одной машине

- Каждый процесс воркера: свой **`WORKER_ACCOUNT_ID`**, свой **`WORKER_INSTANCE_NAME`**, своя сессия Windows / свой Roblox PID.
- Общая **PostgreSQL** и общая очередь `tasks`.

Уже поддерживается модель «несколько воркеров» на уровне БД; ограничение — ресурсы сервера и политика Roblox/Windows.

## 7. Чеклист для разработчика (вне ядра репозитория)

1. Скрипт(ы) создания пользователей Windows под аккаунты (однократно при развёртывании).
2. Инжектор + набор Lua: логин, фарм, стоп, трейд, продажи; параметры и файловый IPC согласованы с JSON в README.
3. Доработка **`WindowsGameAdapter`** (или отдельный класс): запуск Roblox от пользователя, `subprocess` к инжектору, учёт PID, перезапуск при падении, остановка по cancel.
4. Переменные окружения: см. **`env.template`** (`INJECTOR_*`, `ROBLOX_*`, и т.д.).

## 8. Плюсы и минусы

**Плюсы:** автоматизация, масштабирование по числу пользователей Windows/RAM/CPU, смена Lua без пересборки Python.

**Минусы:** сложный первоначальный деплой; риск детекта античитом; необходимость сопровождать инжектор при обновлениях клиента.
